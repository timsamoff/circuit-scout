# Integration Checklist — Circuit Scout

Generated by the Sentinel Integration Audit, 2026-09-13. Grounded in this project's actual commit history, not generic best practice — every touchpoint below cites the commit(s) that demonstrate it actually happened.

Recurring units of work: **a circuit entry** (primary) and **a scraper source** (secondary), per `PROJECT_PROFILE.md`.

Surfaces: **public site** (`index.html`/`js/main.js`/`css/style.css`) and **admin dashboard** (`admin.html`/`js/admin.js`/`css/admin.css`), sharing one backend (`server.js`) and one database (`circuits.db`), with `data/circuits.json` as a derived static export. The two surfaces do **not** share a design-token registry (per the design-quality audit) — a touchpoint that requires visual/token changes must be checked in both `css/style.css` and `css/admin.css` independently, not assumed to propagate.

## Part 1 — Touchpoint inventory

### 1. Definition/registry layer — the `circuits` table schema

- **Where**: `server.js`'s `CREATE TABLE IF NOT EXISTS circuits` block (~line 187) and its self-migrating `ALTER TABLE` check (~line 234) for columns added after the table already existed in production.
- **Change required**: add the column to `CREATE TABLE`, AND add a corresponding `ALTER TABLE ... ADD COLUMN` guarded by a `PRAGMA table_info` check (the pattern already established for the `ignored` column) so existing local/deployed databases pick up the new column without a manual migration.
- **Failure mode**: **silent** if only `CREATE TABLE` is updated — a database created before the change simply never gets the new column, and every `INSERT`/`UPDATE` referencing it either errors (loud, if the column is referenced in a fixed-position `INSERT`) or silently omits the data (silent, if using named-column `INSERT`, which this codebase does throughout — so this leans silent).
- **Real example**: commit `2366323` ("Added circuit ignore for unneeded circuits") added exactly this pattern for the `ignored` column — both the `CREATE TABLE` addition and the runtime `ALTER TABLE` migration check were added together, correctly, in the same commit. This is the template a future column addition should follow.

### 2. Persistence/export layer — the JSON export shape

- **Where**: `server.js`'s `autoExportToJSON()` (~line 384), and independently, `force-export.js`'s hand-rolled export mapping, and `fix-duplicates.js`'s own export mapping, and `scraper.js`'s own `autoExportToJSON(db)`.
- **Change required**: a new circuit field must be added to the row-mapping object in **all four** of these places to appear in `data/circuits.json` consistently regardless of which tool last wrote it.
- **Failure mode**: **silent** — the design-quality audit already confirmed `force-export.js` omits `components` and `fix-duplicates.js` omits `id` relative to `server.js`'s version. Running either tool doesn't error; it silently produces a `circuits.json` missing fields the public site depends on (e.g. `id` is required for the favorites feature to function).
- **Real example**: this is a confirmed, currently-existing gap (`sentinel-notes/TODO.md`'s `fix-duplicates-id-bug` and `force-export-components-bug` items), not a hypothetical — the drift already happened and is sitting in the codebase today.

### 3. Rendering/presentation layer — public site card + admin list item

- **Where**: `js/main.js`'s `renderCircuitsList()` (~line 406, builds the public circuit-card HTML) and `js/admin.js`'s `renderCircuitsList()` (~line 229, builds the admin list-item HTML) — two independently-maintained render functions despite the same name.
- **Change required**: a new circuit field that should be user-visible needs template-string additions in both functions independently; a field that should only be admin-visible (e.g. `ignored`) still needs the admin one at minimum.
- **Failure mode**: **silent** — a missing render-layer update doesn't crash anything; the field is just absent from the UI, which looks like the feature was never added rather than an incomplete change.
- **Real example**: commit `236d291` ("Improved circuit editing: now includes all fields") is literally a fix commit for exactly this gap — an earlier edit-circuit form was missing fields that existed in the data model, and this commit went back to add them across `js/admin.js` (1090 lines changed) plus adjustments in `js/main.js` and `css/admin.css`. This wasn't caught until well after the fields existed.

### 4. Interaction/control layer — public/admin filter and form fields

- **Where**: filter dropdowns/buttons in both `index.html`+`js/main.js` and `admin.html`+`js/admin.js`; the manual "Add Circuit" form (`admin.html`'s `#add-circuit-form`) and its edit-modal counterpart (`js/admin.js`'s `editCircuit()`, ~line 551).
- **Change required**: a new filterable/editable field needs: a form input in `admin.html`, read/write wiring in `editCircuit()`'s `saveChanges()`, and (if filterable) a dropdown/button plus `filterState` key and event listener in the relevant `js/*.js` file(s).
- **Failure mode**: **silent** for filtering (a filter that silently does nothing looks like "no results match" rather than "this filter isn't wired up"); **loud-ish** for the edit form specifically, since a field left out of `saveChanges()`'s `updatedCircuit` object gets silently reset to its default on every edit (e.g. if `ignored` had been left out of `saveChanges()`, every edit would silently un-ignore a circuit) — this is silent in the sense that no error appears, but its effect (quietly reverting a field) is more damaging than a merely-invisible new field.
- **Real example**: same commit as #3 above (`236d291`) — the "now includes all fields" framing directly describes this exact gap being closed after the fact.

### 5. Core logic/computation layer — favorites ID handling

- **Where**: `js/main.js` — `favorites` Set construction (~line 58), `toggleFavorite()` (~line 461), `applyAllFilters()`'s favorites branch (~line 211), and the API-mode favorites branch inside `loadMoreCircuits()` (~line 318).
- **Change required**: any change to how circuit IDs are represented (type, source) needs `parseInt`/`isNaN` guards applied consistently across all four of these spots — they were clearly patched incrementally rather than sharing one normalization function.
- **Failure mode**: **silent** — a NaN or type-mismatched ID doesn't crash; it just silently fails to match in the `Set`, so favoriting appears to do nothing, or previously-favorited circuits mysteriously disappear from the favorites filter.
- **Real example**: three consecutive commits — `e6fa6a5` ("Fixing favorites bug"), `0ad5459` ("Fixed weird favoriting bug"), `6d6ed97` ("A little more fine-tuning for favorites (catching NaN values)") — all touching only `js/main.js`, all about the same underlying ID-handling fragility. This is the single clearest "bug found late, fixed incrementally" pattern in the project's history.

### 6. Wiring/registration layer — scraper source types

- **Where**: `server.js`'s `POST /api/feeds` handler (~line 1309) branches on `source_type` (`static_html`, Blogger/blogspot, sitemap-discovered, plain RSS/Atom fallback) with substantially different logic per branch; `scrapeSingleFeedWithProgress` (~line 894) branches again on `feed.source_type`.
- **Change required**: adding a new scraper source kind (a fifth ingestion method beyond the current four) needs a new branch in **both** of these functions, plus a corresponding UI section in `admin.html` (mirroring the existing "RSS Feeds" / "Static HTML Sites" collapsible cards) and JS wiring in `js/admin.js` (`addFeed`/`addStaticSite`-equivalent function).
- **Failure mode**: **loud** for the backend (an unhandled `source_type` falls through to the generic RSS/sitemap path and likely produces a visible scrape failure or wrong-shaped data), but **silent** for the UI half — nothing prevents someone from adding the backend logic for a new source type without ever exposing a way to add one through the admin dashboard, which would just look like the feature doesn't exist rather than erroring.
- **Real example**: commit `538c18b` ("Added limited static site scraping functionality / improved random loading") — adding the `static_html` source type touched `admin.html`, `css/admin.css`, `css/style.css`, `js/admin.js`, `js/main.js`, `scraper.js`, and `server.js` in one commit (9 files), confirming this is a genuinely wide touchpoint when done completely.

### 7. Cross-cutting — duplicated detection/decoding logic

- **Where**: effect-type/category/difficulty/verified detection logic exists independently in `server.js` (three separate functions) and `scraper.js` (a fourth, differently-listed implementation); `decodeHtmlEntities` exists independently in `server.js`, `fix-titles.js`, and `fix-descriptions.js` with different entity coverage in each.
- **Change required**: adding a new effect type to the detection vocabulary (e.g. recognizing "Envelope Filter" as a type) needs the same string added to **up to four separate lists**; fixing an HTML-entity-decoding bug needs the same fix applied to **up to three separate functions**.
- **Failure mode**: **silent** — each copy works correctly for its own inputs; the failure only shows up as inconsistent behavior between code paths (a circuit scraped via one path gets typed correctly, the identical circuit scraped via another path doesn't), which reads as data quality noise rather than an obvious bug.
- **Real example**: this is a currently-existing, confirmed gap (design-quality audit Part 1, findings 1-2) rather than a specific past commit — the drift already exists in the present codebase, which is itself evidence nothing has ever caught this category of change needing to happen everywhere at once.

### 8. Cross-cutting — one-off maintenance scripts as a recurring pattern

- **Where**: `fix-duplicates.js`, `fix-titles.js`, `fix-descriptions.js`, `compare-db-json.js`, `force-export.js` — all created as standalone scripts to fix a specific past data problem.
- **Change required**: none, structurally — but this is worth tracking as a *pattern* rather than a single touchpoint, since the project's history shows this happening repeatedly (`check-count.js`, `check-feed-total.js`, `fetch-all-pages.js`, and `test-feed.js` were created and later deleted in commits `28230da`→`3a5ed35`, a nearly identical create-then-abandon cycle to the currently-existing `fix-*.js` files).
- **Failure mode**: **silent**, in the sense that these scripts accumulate quietly and drift from the main server logic (see #2 and #7) without any signal that they need to be revisited or retired once their one-off purpose is served.
- **Real example**: `check-count.js`, `check-feed-total.js`, `fetch-all-pages.js`, `test-feed.js` were all added in `28230da` and deleted just one commit later in `3a5ed35` — direct evidence this project has a recurring habit of spinning up throwaway diagnostic scripts, some of which get cleaned up and some of which (the current `fix-*.js` files, `compare-db-json.js`) don't. Not gateable as a hard rule, but worth a standing note (see Known Gaps).

### 9. Documentation — README feature list

- **Where**: README.md's `## ✨ Features` bullet list.
- **Change required**: a user-facing capability change should update the matching bullet.
- **Failure mode**: **silent** — nothing breaks; the README just quietly stops matching reality, exactly as already found and documented in the design-quality audit (the "Smart detection... identifies effect types, difficulty, and components" bullet overstates automatic component detection, which doesn't actually exist).
- **Real example**: the components-detection README claim, confirmed stale in the prior audit, is direct proof this drift already happened and wasn't caught until an external audit looked for it.

## Part 2 — CLAUDE.md, README, DESIGN.md, and TODO.md gate checks

### CLAUDE.md gate (highest priority)

**Trigger**: any commit that adds/changes a circuit field, a scraper source type, an API endpoint, or a structural fact recorded in `CLAUDE.md`'s "Architectural facts worth knowing before editing" section.

**Requirement**: `CLAUDE.md` must be touched in the same commit. If not: block (or warn, per whichever the Gate-Check Implementation prompt wires up) with a message naming which section of `CLAUDE.md` plausibly needs updating (e.g. "this commit adds a scraper source type — update CLAUDE.md's Architectural facts section").

### README gate

**Trigger**: any commit that changes user-facing behavior, setup/run instructions, or the feature list `index.html`/`admin.html` actually implement.

**Requirement**: README.md must be touched in the same commit if the change affects:
- The feature-list bullets under `## ✨ Features`.
- Setup/usage instructions — **currently there are none in the README at all** (confirmed gap from the design-quality audit's Part 10). Until `sentinel-notes/TODO.md`'s `readme-setup-instructions` item is resolved, this specific sub-check has nothing to verify against; the gate should still fire on setup-affecting changes (e.g. a new required `.env` variable) so the gap doesn't silently grow, but the message should note the baseline is currently incomplete rather than implying a regression from a previously-accurate state.

### DESIGN.md gate (narrower trigger — confirmed with the user)

**Trigger, confirmed**: DESIGN.md must be updated for:
- A new scraper source/subsystem type beyond the current four (RSS/Atom, WordPress RSS, sitemap-discovered, static-HTML).
- A structural change to the public/admin data-flow split (e.g. the admin dashboard gaining a static-mode equivalent, or the public site's live-API/static-JSON split changing).
- Consolidating the two CSS token systems into one shared source (a structural fact DESIGN.md explicitly documents as currently *not* the case).

**Does NOT trigger** DESIGN.md (CLAUDE.md gate above still applies): adding a circuit field, adding a filter, a UI-only tweak, adding a new effect-type keyword to the detection vocabulary, fixing a duplicated-logic bug without changing the overall structure.

### TODO.md sync gate (split hard/soft per the audit's own guidance)

- **Hard check** (mechanically verifiable): for any commit that modifies a `sentinel-notes/*-design-brief.md` file, verify the commit also modifies `sentinel-notes/TODO.md` (per this project's confirmed convention: completed items are deleted outright, and their linked brief is deleted alongside them — so in practice, a commit that deletes a design-brief file should also remove its corresponding TODO.md line in the same commit). Block if the brief changed but TODO.md didn't.
- **Soft check** (non-blocking reminder): for plain one-line TODO.md items with no linked brief, there's no reliable commit-diff signal to correlate against — the gate check should not attempt to guess which commit resolves a plain item. Instead, surface a periodic non-blocking reminder (as part of the full-repo scan mode, not per-commit) listing TODO.md items older than some threshold with no recent related activity, purely as a nudge.

## Part 3 — Deliverables

### Gate-check logic (plain description, for the Gate-Check Implementation prompt to build)

**Commit-time check** (runs as a `pre-commit` or `commit-msg` hook, fast, diff-scoped only):

1. Read the staged diff's file list.
2. If the diff touches `server.js`'s `CREATE TABLE circuits` block or adds a new column reference anywhere → require `server.js`'s `ALTER TABLE ... ADD COLUMN` migration-check block to also appear touched, and require `CLAUDE.md` touched. (Touchpoint #1)
3. If the diff touches any one of `server.js`'s `autoExportToJSON`, `force-export.js`, `fix-duplicates.js`'s export mapping, or `scraper.js`'s `autoExportToJSON` → warn (not hard-block, since a legitimate single-file fix is common) that the other three export-mapping functions should be checked for the same field, listing their file paths. (Touchpoint #2)
4. If the diff touches `js/main.js`'s `renderCircuitsList` or `js/admin.js`'s `renderCircuitsList` but not both → warn, naming the other file, unless the change is clearly surface-specific (the hook can't reliably tell — treat this as always a warn, never a hard block). (Touchpoint #3)
5. If the diff touches `admin.html`'s `#add-circuit-form` or `js/admin.js`'s `editCircuit`/`saveChanges` but not the other → warn. (Touchpoint #4)
6. If the diff touches `server.js`'s `/api/feeds` POST handler's branching logic or `scrapeSingleFeedWithProgress`'s branching but not both, and not `admin.html`'s feed-source UI sections → warn, listing all three. (Touchpoint #6)
7. If the diff touches any of the four effect-type/category detection functions (two in `server.js`, one in `scraper.js`, or the entity-decoding trio) → warn, listing the sibling files, since a hard block here would be too disruptive until the consolidation TODO item is resolved. (Touchpoint #7)
8. If the diff changes anything under `index.html`'s feature-facing markup, `admin.html`'s feature-facing markup, or adds a new npm script/env var → require README.md touched, or warn if the change is judged (by the hook's file-list heuristic) to be UI-only rather than capability-adding. (README gate)
9. If the diff modifies any `sentinel-notes/*-design-brief.md` file → require `sentinel-notes/TODO.md` also touched. Block if not. (TODO.md hard gate)
10. If the diff plausibly represents a new subsystem/structural change (heuristic: a new top-level file matching a source-type pattern, or a diff touching more than N files across both `css/style.css` and `css/admin.css` simultaneously) → warn that DESIGN.md may need updating, per the confirmed narrower threshold. This is inherently fuzzier than the other checks and should stay a warn, not a block.

**Full-repo scan mode** (runs via a CI-scheduled job if CI is ever re-enabled, or as a `pre-push` hook otherwise — not on every commit):

- Re-check every touchpoint category above across the full current state of the repo, not just a diff, to catch drift introduced outside a single commit (manual edits, a merge, or an interaction between two independently-valid commits).
- Specifically re-verify: do all four export-mapping functions (touchpoint #2) currently produce the same field set? Do the two `renderCircuitsList` functions (touchpoint #3) currently expose the same circuit fields (accounting for intentional public/admin differences like `ignored` being admin-only)? Do the detection-logic copies (touchpoint #7) currently have matching effect-type lists?
- Surface the TODO.md soft-reminder (items with no linked brief, stale beyond a threshold).
- Output format for every flagged item, commit-time or full-scan: the specific rule/category name, the exact file(s) involved (and line numbers where the check is grep/diff-based), and either the required correction or a concrete self-review question (e.g. "Does the admin edit form's `saveChanges()` include this new field? Check `js/admin.js` around line 661.").

### Commit conventions (Part 4, confirmed with the user)

- **Style**: terse one-line plain-English summaries, no prefix scheme (no Conventional Commits `feat:`/`fix:`). Matches existing history and the user's stated global preference. A body is only added when genuinely needed (a few short bullet sentences, never a narrative), consistent with the user's global commit-style preference.
- **Granularity**: one commit per session/logical change as the default; multiple atomic commits are acceptable for a change with genuinely distinct logical parts (as this session itself did — license fix, comment cleanup, and doc-scaffolding were split into three commits because they were three different concerns), but splitting isn't the default expectation.
- **Attribution stripping**: the `commit-msg` hook must actively strip or reject any co-author/attribution trailer (e.g. a "Generated with Claude Code" line or `Claude-Session:` trailer), regardless of in-session instruction compliance. This is hygiene, not style, and applies regardless of the above preferences.
- Recorded in `CLAUDE.md` (not just here) so the convention survives even if the hook is ever missing or broken — see the update made to `CLAUDE.md` alongside this checklist.

### Exceptions mechanism (Part 5)

- **Standing exceptions**: `sentinel-exceptions.json` at the repo root (no existing project convention to match instead). Each entry: `{ "rule": "<category>", "files": ["<narrow path, no globs>"], "reason": "...", "owner": "...", "reviewBy": "YYYY-MM-DD" }`. An expired `reviewBy` fails the same as no exception. Proposed structure only — not created yet, since no exception is currently needed; this is scaffolding for the Gate-Check Implementation prompt to wire up.
- **One-off overrides**: a commit trailer `Sentinel-Override: <reason>` for a single commit that's a legitimate one-time exception (e.g. an unusually large but justified refactor commit) — no owner/expiry needed since it only ever applies to that one commit.
- Both mechanisms require a recorded reason; neither is self-granted by an agent mid-session without the user's involvement — exceptions are proposed to the user as part of a flagged violation, not created and silently applied.

### Deviations from the original proposal and why

- The **feed-source-parity check** narrowed from a three-file correlation to a two-file one — this is a real precision loss, but the alternative (parsing JS to identify which specific branch inside `server.js` changed) was out of scope for a regex/diff-based check.
- The **TODO.md sync check's mechanism** changed entirely (git-diff-based → working-tree-hash-based) because the original proposal's premise — that a git diff could see `sentinel-notes/` changes — doesn't hold once that directory is gitignored (a fact confirmed during Part 11 of the Design & Code Quality Audit, after the Integration Audit's proposal was written). This is exactly the kind of thing Part 1 of this prompt asks to catch and adjust for, not implement blindly.
- The **CLAUDE.md gate's trigger** is broader (any `server.js` change) than the checklist's more precise language ("a circuit-field/schema change, a new endpoint, or an architectural fact") because a regex-based check can't reliably distinguish those sub-cases from an unrelated `server.js` edit without a real parser. Accepted as a known over-trigger for an advisory-only check — a warning that fires slightly too often is a much smaller cost than one that misses real cases.

### Backlog found by the report-only pass (Part 4)

A full-repo scan was run before this check was made blocking-capable, specifically to establish the baseline the full-scan mode's blocking logic uses. Result: **zero pre-existing blocking violations** — the only rule capable of blocking (`todo-sync`) has no meaningful "prior state" until the snapshot mechanism has run at least once, so there was nothing to grandfather in. `sentinel-gate/baseline.json` was written as an explicit empty baseline (not left absent) so this is a recorded fact, not an assumption.

The advisory findings the full scan does surface on every run (export-field-parity ×3, detection-logic-drift, and — in full-scan mode specifically — a CLAUDE.md-touched false-positive-shaped warning since "all tracked files" always includes `server.js`) all correspond to items already tracked in `sentinel-notes/TODO.md` (`fix-duplicates-id-bug`, `force-export-components-bug`, `detection-dupe`, `decode-html-dupe`) — no new TODO items were needed, since this pass didn't surface anything the prior audit hadn't already found.

## Known gaps (not mechanically gateable)

- **Duplicated effect-type/category detection logic (touchpoint #7)** can be *flagged* by the commit-time hook (touching one copy warns about the sibling) but the hook cannot verify the copies are actually semantically consistent — only that someone was reminded to check. Genuinely fixing this requires the consolidation work tracked in `sentinel-notes/TODO.md` (`detection-dupe`); until then, this stays a reminder-level gate, not a verified one. **Resolved 2026-09-14**: the HTML-entity-decoding half of this touchpoint (`decodeHtmlEntities`, previously duplicated across `server.js`, `fix-titles.js`, `fix-descriptions.js`) was consolidated into a shared `decode-html-entities.js` module — the gate check's `detection-logic-drift-warn` rule was updated to stop watching `fix-titles.js`/`fix-descriptions.js`, since they no longer contain any duplicated logic.
- **One-off maintenance script proliferation (touchpoint #8)** has no mechanical trigger at all — there's no reliable signal distinguishing "a legitimate new diagnostic script" from "another copy of logic that already exists elsewhere." This is a standing risk to revisit manually/periodically (e.g. during a future design-quality audit re-run), not something this checklist can gate.
- **Automated accessibility testing** — flagged as a candidate in the prior audit, but this project has no test framework or CI currently active, so there is no infrastructure this gate check can hook into yet. Would need `PROJECT_PROFILE.md`-level tooling decisions (adding a test runner, re-enabling CI) before it's gateable, which is out of this checklist's scope.
- **Resolved 2026-09-14**: the scraper.js runtime bug is no longer an open precondition. Confirmed with Tim: `scraper.js`'s broken standalone RSS/Atom pipeline was dead code (`server.js` never called into it), and the "run a scrape locally before pushing" need it was meant to serve is already covered by `server.js`'s own working pipeline via the admin dashboard. The broken code, the `node scraper.js` direct-invocation entry point, and the `npm run scrape` script were removed rather than fixed. The "scraper runs without throwing" smoke-test candidate from the prior audit is no longer meaningful as originally scoped, since there's no longer a standalone entry point to smoke-test — if a future test is wanted here, it would target `scrapeStaticListing`/`scrapeStaticProjectPage` (the code that remains) or `server.js`'s own scrape pipeline instead.
- **README setup-instructions gap** is real but pre-existing (not a regression this checklist can detect against a "should have had it" baseline) — the README gate above can prevent it from getting *worse*, but closing the existing gap is manual work tracked separately (`readme-setup-instructions` in TODO.md).
- **The TODO.md sync check's working-tree-hash mechanism** (built to work around `sentinel-notes/` being gitignored) fires on "changed since the last time any check ran," not "changed in this specific commit." This means: (1) a change made and then reverted between two check runs is invisible to it — the hash returns to its prior value with nothing to flag; (2) if the hook is skipped for one run (e.g. `git commit --no-verify`, or the manual command isn't run), the next run's comparison spans two logical changes at once, which could either mask a violation or misattribute it. This is a structurally different (weaker) guarantee than every other rule's real git-diff-based check, and is disclosed here rather than presented as equivalent.
- **The TODO.md sync check's unlinked-item half** (a non-blocking periodic reminder for plain TODO.md items with no linked brief, per the Integration Audit's own scoping) was not built this pass — it needs a CI schedule or equivalent to run periodically without manual invocation, and this project has neither. Deferred, not implemented.
- **The CLAUDE.md/README/feed-source/render/edit-form advisory checks all use file-level triggers** (did file X change) rather than semantic ones (did the specific *kind* of change that matters happen) — a regex/diff-based check without a real JS/HTML parser can't reliably tell "added a circuit field" from "fixed a typo" within the same file. This means these checks will sometimes warn on changes that don't actually need the paired file touched (a false-positive-shaped nudge), which was accepted as the right tradeoff for an advisory-only, cheap-to-run check — see "Deviations from the original proposal" above.
